The mental model: two planes + a clock

Everything in cluster_link/ is one of: control plane (what should exist — replicated, raft-backed), data plane (move the bytes — per-partition, leader-driven), or a periodic task that bridges the remote source into the control plane. Status reporting reads across both.

Periodic tasks — the source→control-plane bridge

All extend the abstract task (task.h:33), a periodic state machine with run_impl(). Each maps 1:1 to a docs "shadow link task". They discover remote state and emit control-plane commands; they do not move record bytes.

Schema Registry is mirrored two ways: topic mode (replicate the _schemas topic via the data plane) or API mode (call the source SR HTTP API). Config in model/types.h:519.

Reporting

service (service.h:41) + rpc_service (rpc_service.h:21) aggregate per-partition lag and per-task health across brokers for the status API. RPC surface defined in shadow_linking_rpc.json.

Three facts that anchor everything

  1. Active-passive, asynchronous. Source serves traffic; shadow is read-only until failover. Always some lag. [docs]
  2. Byte-level, offset-preserving. Records are copied, not re-produced — offsets & timestamps are identical to source.
  3. Control plane decides, data plane copies, tasks discover. If you can place a file in one of those three buckets, you understand its job.
