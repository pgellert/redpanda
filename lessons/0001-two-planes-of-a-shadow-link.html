Lesson 0001 · Shadow Linking

The two planes of a shadow link

Mission: durable code-ownership model of src/v/cluster_link/. This lesson gives you the skeleton everything else hangs on.

Your win today → Given any file in cluster_link/, you can name which of four buckets it lives in — and therefore what its job is — without reading it.

1 · What a shadow link is

"Shadowing" is Redpanda's enterprise disaster-recovery feature (25.3+). It establishes asynchronous, offset-preserving replication from a source cluster to a read-only shadow cluster. The shadow continuously pulls data; on disaster you fail over and it becomes writable. [docs: overview]

Two phrases to internalise, because they explain the whole code shape:

  • Active-passive & async → the shadow never writes its own data; it only mirrors. There is always lag. This is why the data plane is a one-directional pull loop, not a consensus protocol.
  • Byte-level, offset-preserving → records are copied, not re-produced. Offset 42 on the source is offset 42 on the shadow. This is why replication appends raw batches to raft rather than going through the produce path.

In the code the feature is the cluster_link module, a link is a link, and a shadow topic is a mirror topic. (Full naming map: architecture-map reference.)

2 · The four buckets

Every file in cluster_link/ serves one of four jobs. This is the load-bearing idea of the whole lesson:

control plane — decides what should exist. A raft-replicated state machine on the controller: the desired set of mirror topics and their states. Owns commands and reconcilers.
manager.h:38 · link.h:32 · topic_reconciler.h:24 · link_status_reconciler.h:28 · model/types.h:1021 (link_state), :1077 (commands)

data plane — moves the bytes. On each shard leading a mirror partition, a loop fetches records from the source over Kafka and appends them to the local raft log, offset-for-offset.
replication/link_replication_mgr.h:27 · replication/partition_replicator.h:57 · replication/deps.h (data_source/data_sink)

periodic task — bridges source → control plane. Each extends the abstract task (a timer + run_impl() state machine). It polls the remote source and emits control-plane commands. Three of them: topic sync, consumer-group offsets, ACLs.
task.h:33 · source_topic_syncer · group_mirroring_task · security_migrator

reporting — reads across the others. Aggregates per-partition lag and per-task health from every broker to answer the status API.
service.h:41 · rpc_service.h:21 · shadow_linking_rpc.json

The crucial distinction beginners miss: tasks discover, the data plane copies. The topic-sync task does not move record bytes — it just tells the control plane "a topic named X exists on the source, please create a mirror for it." Only partition_replicator ever touches records.

3 · Retrieve it (don't just read it)

Classify each file into its bucket. Answer from memory — getting one wrong and seeing why is worth more than reading the section again.

1. replication/partition_replicator.cc
2. security_migrator.cc — syncs ACLs from the source
3. topic_reconciler.cc — creates local topics to match desired state
4. rpc_service.cc — aggregates partition reports across brokers
5. link_status_reconciler.cc — drives failover/promotion transitions
6. source_topic_syncer.cc — discovers source topics, emits add_mirror_topic_cmd

4 · A subtlety to chew on

source_topic_syncer is a controller_locked_task (task.h:148), whereas group_mirroring_task is a plain task running on the brokers that host __consumer_offsets. Why would topic discovery be locked to the controller but consumer-group offset sync not be? Hold that question — it's the seed of Lesson 0002 (where tasks run, and why).
