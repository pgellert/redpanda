1 · Two modes, one config

schema_registry_sync_config (model/types.h:519) is a per-link config (Lesson 0003) with two mutually exclusive modes:

ModeHow schemas reach the shadowReuses

shadow_entire_schema_registry		 The internal _schemas topic is mirrored as an ordinary mirror topic — byte-for-byte, offset-preserving, via the data plane. The local SR just reads its own replicated _schemas. Lesson 0004 the data plane

2 · The write gate — is_topic_mutable's schema-registry sibling

Just as a mirror topic blocks client produce while shadowing (Lesson 0005), a shadowed SR blocks client schema writes. The seq_writer checks it on every sequenced_write (pandaproxy/schema_registry/seq_writer.h:174), and the rule has two dimensions — the source of the write × the mode (cluster/cluster_link/frontend.cc:336-344):

write_source \ modeTopic modeAPI mode
client (a normal SR API user)blockedblocked
schema_registry_sync (the shadow importer)blockedallowed

Read the one asymmetric cell: in topic mode even the sync importer is blocked, because the data plane owns _schemas — writing schemas through the SR path would collide with the byte replicator (the same single-writer discipline that makes shadow topics read-only). In API mode, the sync importer is precisely how schemas arrive, so it's the one writer allowed through.

This is your foundation commits, in one table. "distinguish sync writes from client writes" + "expose internal Schema Registry writes" + "internal sequencer write paths" exist to create the schema_registry_sync write source — the lane that's open in API mode while the client lane is shut. It's the exact analogue of the produce gate: is_topic_mutable for topics, link_disables_schema_registry_writes(md, source) for schemas.

3 · Anatomy of schema_registry_mirroring_task (API mode) — all five patterns

Your task (cluster_link/schema_registry_sync/schema_registry_mirroring_task.h) is a recombination, not an invention:

Part of your taskPattern you already own
It's a task that leads _schemas/0 (leads_schema_registry_partition) — "mirroring how the consumer-group task follows __consumer_offsets leaders" Lesson 0002 · LR-0001 locality follows the state it writes

The loop is itself a reconciler: target_has_version(subject, version) is the "is reality already converged?" check, and importing the missing pairs is the convergence — idempotent and re-runnable, like every reconciler in this subsystem.

Honest scope note: per the header, the current increment is PR0: default context only — no filtering, references, compat/mode, deletes, or unsupported-feature handling yet. The source_reader already carries the vocabulary for the rest (unsupported_feature, source_filter contexts/subjects), so the shape is laid for those increments.
