Lesson 0003 · Shadow Linking

How the cluster agrees on what to mirror

The control-plane hand-off: a command emitted on one shard becomes topics on every broker — the heart of code ownership.

Recall (Lesson 0002 cliffhanger): source_topic_syncer is a controller_locked_task — it runs on exactly one shard cluster-wide and emits add_mirror_topic_cmd. Today: what happens to that command.
Your win today → Trace the full path task → command → replicated table → reconciler → real topic with the right types at each hop, and explain the desired-state / reconcile split that makes it safe.

1 · The naming trap: two "cluster_link"s

Before the trace, untangle a directory collision that confuses every new owner:

PathIsHolds
src/v/cluster_link/the enginetasks, replicators, reconcilers — the runtime work
src/v/cluster/cluster_link/the controller statefrontend (writes raft) + table (replicated state)

The engine never touches raft directly. It calls the abstract link_registry (cluster_link/deps.h:31, "accessors to cluster link table"); the concrete implementation is the controller-side frontend+table. That seam is dependency inversion — it's why the engine is testable without a real controller, and it's the cleanest mental boundary in the whole subsystem.

2 · The hand-off, hop by hop

── runs on ONE shard (controller leader) ────────────────────────────── source_topic_syncer::submit_commands (source_topic_syncer.cc:572) └─▶ link->add_mirror_topic(cmd) ── via abstract link_registry (deps.h:31) └─▶ cluster::cluster_link::frontend::add_mirror_topic (cluster/cluster_link/frontend.h:61) └─▶ replicate through CONTROLLER RAFT (holds controller_stm*) ── applied on EVERY node, when the raft entry commits ────────────────── cluster::cluster_link::table::apply_update(record_batch) (cluster/cluster_link/table.h:72) └─▶ mutates in-memory link_state: topic → mirror_topic_metadata └─▶ notifies listeners (register_for_updates, table.h:78) ── reacts on the CONTROLLER LEADER only ─────────────────────────────── manager::on_link_change → if _is_controller_leader: (manager.cc:650-653) topic_reconciler::trigger(link_id) └─▶ execute → do_reconcile_topic → maybe_create_mirror_topic (topic_reconciler.h) └─▶ kafka::data::rpc::topic_creator ── creates the real local topic └─▶ (topic creation is itself a controller op ⇒ exists cluster-wide)

Read the three bands as three different localities: emitted on one shard, applied on every node, reconciled on the leader. The middle band is just "everyone learns the desired set"; only the bottom band takes action.

3 · The pattern: desired state vs reconcile

This is the Redpanda controller pattern, and naming it is most of the understanding:

  • A command records intent, not action. add_mirror_topic_cmd doesn't create anything — it appends "this topic should be mirrored" to replicated state. Same shape as the rest of the controller (topics_table, security, …): a sub-STM (apply_update/apply_snapshot) plugged into the controller log.
  • A reconciler converges reality toward intent. topic_reconciler compares desired link_state against actual local topics and makes up the difference (maybe_create_mirror_topic / maybe_update_existing_topic). It is idempotent and re-runnable — exactly like the task reconciler from Lesson 0002. Same shape, different layer.
The subtlety that prevents chaos: the table is applied on every node (so all nodes know the desired set, e.g. for status/snapshots), but the reconciler only acts on the controller leader (manager.cc:652). That's why you don't get N brokers racing to create the same topic — intent is global, action is single-writer. Same "follow the leader" principle as task locality, one layer up.

The topic now exists on every broker, with raft partitions and leaders. But it's empty. Nothing has copied a single record from the source yet. Who notices the new mirror partition, starts a partition_replicator on its leader shard, and how does that loop preserve source offsets byte-for-byte?
