Lesson 0002 · Shadow Linking

Where the work runs

You derived the rule last time — task locality follows state locality. Now: the one predicate that enforces it, and the pattern it shares with the data plane.

Recall first (no scrolling): consumer-offset sync runs on every shard that leads a __consumer_offsets partition; topic-sync runs on a single shard cluster-wide. State says where work runs. This lesson is how the code asks the question.
Your win today → Read any task's should_start_impl and state exactly where in the cluster it runs — and explain how it follows leadership as it moves, using the same machinery the data-plane replicators use.

1 · One predicate, asked on every shard

A link is a sharded object — it exists on every shard of every broker. On a timer, each shard's copy runs the task reconciler (link.h:134 run_task_reconciler), which asks, for each task it knows about, a single question:

should_start(shard, node) = is_enabled() && should_start_impl(shard, node) // task.cc:216 should_stop (shard, node) = should_stop_impl (shard, node) // task.cc:225

That's the entire location mechanism. The base task handles the timer, the state machine, retries; subclasses answer only "should I be running on this particular (shard, node)?" Because every shard asks independently and continuously, the set of places a task runs is always reconciled toward the truth — no central dispatcher hands out assignments.

Notice the symmetry with should_stop_impl: controller_locked_task stops itself precisely when it is no longer the controller leader (task.cc:255). Start and stop are the same predicate, negated — which is what makes the task chase leadership.

4 · The pattern under all of it

Step back and the whole module is one shape: reconcile running work to current leadership. A controller-locked task, a per-partition offset syncer, and a per-partition partition_replicator are three instances of "start work on the shard that leads the relevant raft group; stop it when leadership moves." Once you see that, the data-plane lesson (0004) will feel like a special case you already understand — the "work" is just a fetch→append loop instead of a task.

5 · Chew on this → Lesson 0003

The controller-locked tasks emit commands (add_mirror_topic_cmd, …) that mutate link_state. But those commands go through controller raft and are applied on every node, while the task that emitted them ran on one. How does a command produced on the controller leader become local topics on every broker? That hand-off — task → command → replicated state → reconciler → real topics — is the control-plane deep dive.
