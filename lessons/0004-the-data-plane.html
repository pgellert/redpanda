Lesson 0004 · Shadow Linking

The data plane: copying bytes, preserving offsets

The topic exists but it's empty. Now we move records — and keep their offsets identical to the source. This is the "byte-level, offset-preserving" promise, in code.

Recall: the control plane (Lesson 0003) created the mirror topic on every broker, with raft partitions and leaders. The data plane is the replication/ bucket — and per Lesson 0002 you already know its shape: start work on the shard that leads the partition, stop on leadership loss. The "work" is one partition_replicator.
Your win today → Trace one fetch→replicate iteration, and explain the mechanism by which a record at source offset 42 lands at shadow offset 42 — plus the three guards that keep that true under failure.

1 · The loop

A partition_replicator (replication/partition_replicator.h:57) is started on the mirror partition's leader shard, fenced by the term_id it was created in (:61,71). Its core is fetch_and_replicate (partition_replicator.cc:251):

while (running): units = get_units(_max_requests, 1) // ← pipeline gate: max 5 in flight (.h:118) data = _source->fetch_next() // ← Kafka FETCH to the SOURCE cluster (external) maybe_synchronize_start_offset() // ← prefix-truncate if source head moved if data.batches empty: continue // ← caught up; loop replicate_and_wait({begin = batches.front().base_offset(), // ← SOURCE offsets, kept as-is end = batches.back().last_offset(), ...}) └─▶ _sink->replicate(batches, ...) // ← append to LOCAL raft (service.cc:427) └─▶ result handled ASYNC (handle_replication_result) // ← so the loop keeps fetching

Two ends, two protocols: fetch talks Kafka to the source (remote_partition_source); replicate is a local raft append (local_partition_sink). No internal RPC in between — the replicator runs at the leader (your RPC-philosophy finding). Up to 5 requests pipeline via a semaphore (.h:118-120); last_replicated_offset is bumped eagerly so the next fetch can start before the previous append commits.

2 · How offset 42 stays offset 42 (the crux)

Fetched batches carry their source base_offset/last_offset. The sink does not let raft assign fresh offsets — it passes the source offsets through explicitly (service.cc:449-497):

expected_offsets = [ batch.base_offset() for batch in batches ] // the SOURCE offsets _replicator->replicate(batches, expected_offsets, _last_replicated_offset, ...) // ▲ "land these batches at EXACTLY these offsets"
This is the entire meaning of offset-preserving: the local log is told the offsets rather than minting them. That's also why a shadow topic is read-only — any independent local write would mint an offset and break the 1:1 mapping. (Recall the docs: writing to shadow topics is blocked while shadowing is active.)

3 · The three guards that keep it correct

Monotonicityoverlapping / duplicate fetches writing backwards require new_begin & new_end > last_replicated; else throw monotonicity_violation_exception → step down → recover next term service.cc:464; partition_replicator.cc:279

Start-offset syncsource retention trimming its head out from under us if source start > shadow start, prefix_truncate the shadow to realign partition_replicator.cc:319 (maybe_synchronize_start_offset)

The producer-ID guard is your first glimpse of failover correctness — the data plane is quietly preparing for the day the shadow becomes writable. Hold that thread.

4 · Failure & recovery

Any exception in the loop (a failed append, a monotonicity violation, a dead source connection) is caught (partition_replicator.cc:277-298), the in-flight gate is drained, then: reset the sink, reset the source to next_offset(last_replicated) (or the configured start offset if nothing replicated yet), back off, and retry. Start-up itself is resume-aware: if the sink already has data, replication resumes from next_offset(last_replicated_offset) rather than the configured start (partition_replicator.cc:57-70). The replicator is, like everything else here, a convergent retry loop.
