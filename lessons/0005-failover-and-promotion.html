Failover & promotion

The shadow has been read-only this whole time. This is the moment it can become writable — and where the subtle correctness questions live, including the failover-identity debate.

Recall: the data plane (Lesson 0004) preserves offsets and quietly prepares for failover (producer-ID sync). The status RPC (your RPC investigation) gathers per-partition leadership. Failover is where both pay off — driven by the link_status_reconciler on the controller leader.
Your win today → Narrate the mirror_topic_status state machine, distinguish failover from promotion, explain how the reconciler decides a topic is safely failed over — and state precisely what identity is and isn't preserved.

2 · Failover vs promotion — one word of difference

They reach the same place (a writable topic) by different paths. The enum comments say it exactly:

failing_over → failed_overpromoting → promoted
Triggerdisaster — source is goneplanned migration — source is healthy
Replicationstop now, unblock writes immediatelywait to catch up to source first, then cut over
Data losspossibly (whatever hadn't replicated)none (drains the lag first)
Codetypes.h:124-132 — "promoting … additionally waits for the topic to catch up to the source"

3 · How the reconciler finishes a failover

Operator triggers it (rpk shadow failover → frontend → batch_update_mirror_topic_status_cmd sets active → failing_over via controller raft). Then on the controller leader, link_status_reconciler (link_status_reconciler.h:28) converges the rest — and it leans on the report RPC you already studied:

try_finish_failover(topic): (link_status_reconciler.cc:107) report = shadow_topic_report(link, topic) ── the cross-broker status RPC rev = get_last_update_revision(link) ── revision the controller has for the link valid = { partitions whose leader's broker has link_update_revision >= rev } (:144-152) if valid.size() == report.total_partitions: (:153) update_mirror_topic_state(topic, failed_over) ── the cut is complete else: defer (not all partition leaders have unblocked writes yet)

The link-revision check (cc:127-133) is the clever bit: a partition leader only bumps to the link's update revision once it has processed the failing_over command and unblocked the Kafka API for that mirror topic. So "every partition reports a leader at revision ≥ controller's revision" is a proxy for "every partition is actually writable now." The code itself calls this a reasonable heuristic, not foolproof — a phrase worth remembering when you review changes here.

5 · Split-brain — the operational guardrail

Failover makes the shadow writable but cannot make the source stop. If clients keep writing to a still-alive source after you fail over, both clusters accept writes independently → split brain. That's why Shadowing is active-passive, manual failover, with the docs' instruction to repoint all clients before resuming writes, and why failed_over/promoted have no automatic path back to active yet. The system enforces single-writer discipline by process, not by protocol.
